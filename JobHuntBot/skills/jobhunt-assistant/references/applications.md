# 选定岗位、准备申请与提交

## 确定本次阶段

先读用户指定的 `lead_id` 或精确岗位，以及当前两池、跟进记录，避免重复投递。只有“转入总岗位池”不等于授权填写或上传；“准备投递/帮我填写这个岗位”可授权该岗位的草拟、填表及所需材料上传，最终提交仍按审阅与明确授权执行。“自动投递流程”或安装本技能本身不授权批量申请。

如果待处理的是预备池岗位，转入总池须有用户给出的明确 `lead_id` 与推进意图；不能按收藏、排名、P1 或模型推测擅自晋升。用户只给公司时先列具体职位和单公司申请名额限制，让其选定。直接给出精确官方岗位的申请请求可按通用 JobHuntBot 流程建正式记录，无需人为绕道再索要一个不存在的 lead_id。

## 转入总池

- 精确匹配 lead_id；不存在或有重复 ID 时先解决定位。核对岗位仍开放、用户毕业资格、现有阻碍，以及两池和跟进中是否已有该申请。
- 按公司/岗位/地点/官方 URL 去重，并核对 ATS 岗位 ID。已有正式记录时关联和更新必要证据，不能覆盖 Submitted/Offer/Rejected 等状态，也不能重复申请。
- 按 `job_pool.csv` 当前表头映射已核实字段。合适且无重要缺口用 Pending；需用户事实或资格决策用 Needs user；记录来源 lead_id 和下一步。按当前证据明确填写 `cohort_match_status` 为 Yes/No/Unclear，不靠备注推断。不要凭晋升操作设置 Submitted。
- 原预备行记录 `user_decision` 及 `promoted_at`（有时区的实际时间），保留追溯和原筛选状态，不新造看板不支持的状态值。不要删除原线索。当前看板按公司/岗位/地点/URL 合并显示，匹配正式池的状态优先。

## 准备、填表与审核

读取 `J/candidate_profile.json`、`J/application_rules.md`、`J/resume_routing.md`、`J/answer_bank.md`、`J/experience_bank.md`、`J/references/application-playbook.md`。遇到验证码时再读 `J/references/verification-code-workflow.md`；隐私、登录或分享问题参考 `J/references/safety-and-boundaries.md`。

按用户的简历策略和实际 JD 选择有证据支持的 2–4 段经历（不足则如实使用更少）。候选材料只从当前用户源文件读取；不要把技能中的说明当作表单个人资料。特别核实成绩与项目指标口径：未提供总 GPA/WAM 时不能换算或编造，团队项目结果不能写成个人独立指标。简历版本遵循路由并核验文件确实存在；保留中文基础版、版式和照片比例。

复用已确认的答案，检查 ATS 解析后的教育、日期和当前就业状态。清晰低风险字段直接填写；缺失或矛盾的重要事实集中问一次，并继续其他独立准备。上传后检查附件名称、版本、成功状态和解析结果。遇到登录/2FA/权限障碍记录实际页面与下一步；不能猜账号、绕过验证或不断重试。

最终提交前提供具体审阅摘要：公司与职位/编号/城市、资格判断、简历版本和选中经历、关键回答及薪资、未解决项。等待用户对此申请的明确提交授权；同一申请和内容的有效授权已给出则不要重复请求。内容或岗位有实质变化需要重新审阅。

## 提交证据与回写

授权后通过真实页面提交，并核验成功文字、提交状态、确认页面/申请编号等上下文一致的证据；只有 URL 包含 `confirmation` 或点过按钮不够。结果不明时先核对网站状态，不能盲目重试提交。

成功后更新 job_pool 为 Submitted，在 application_log 记录实际时间、平台、已用简历、关键答案、选用经历、确认依据及官方 JD。`job_description` 保存官方职责与要求的可用文本并注明来源；若工具或内容规则不允许完整复制，保留允许范围和来源并说明缺失，不编造。同步必要 follow_up 与 daily_dashboard；新获用户确认的个人事实回写其资料源。

阻碍或未提交的草稿留在 job_pool、blocker_queue 或既有申请草稿位置，不能创建虚假的成功投递日志。收件通知只证明收件；如另有“申请未完成”提醒，保留冲突和待查门户状态，不能靠通知补造成功证据。
